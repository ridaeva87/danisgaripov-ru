## 1. Краткий вывод

Проект является одностраничным React/Vite-сайтом с динамическими страницами услуг по slug. Основной пользовательский путь: лендинг -> блок услуг -> страница услуги или мини-опрос -> форма заявки -> Google Sheets webhook или локальный Telegram lead API.

Архитектура простая и подходит для аккуратных визуальных и контентных доработок без крупной перестройки. Для будущих интеграций с Telegram Bot API, платежами, CRM и административным контуром потребуется добавить более надежный backend-слой: текущий сервер умеет только отправлять текстовые сообщения в Telegram и не хранит состояние заявок, платежей, анкет и файлов.

## 2. Стек технологий

- Frontend: React 18, TypeScript, Vite 5.
- Роутинг: `react-router-dom` 6.
- UI: Tailwind CSS, shadcn/ui-style компоненты на Radix UI, `lucide-react`, `sonner`.
- Формы: локальное состояние React, отдельные shadcn input/textarea/checkbox компоненты. `react-hook-form` и `zod` установлены, но в текущих формах не используются.
- State/data fetching: `@tanstack/react-query` подключен через `QueryClientProvider`, но фактически в бизнес-логике не используется.
- Backend/API: `server/lead-api.mjs` на встроенном `node:http`.
- Интеграции: Google Apps Script webhook для основной формы; Telegram Bot API через `/api/lead` для квиза и опционального режима `telegramOnly`.
- Сборка/пакеты: есть `package-lock.json`, `bun.lock`, `bun.lockb`; фактически проект содержит npm-структуру `node_modules`.
- Тесты: Vitest + jsdom, пока только smoke-example тест.

## 7. Формы и пользовательские сценарии

### LeadForm

Поля:

- имя, required;
- телефон, required;
- email;
- Telegram;
- "Желаемая сумма";
- комментарий, required;
- чекбокс согласия на обработку персональных данных.

Поведение:

- без согласия форма не отправляется;
- по умолчанию отправка идет в Google Apps Script webhook с `mode: "no-cors"`;
- в режиме `telegramOnly` отправка идет в `/api/lead`;
- после отправки показывается toast и локальный success-блок.

Риски:

- `mode: "no-cors"` не позволяет проверить фактический успех отправки в Google Sheets;
- webhook URL захардкожен во frontend;
- нет серверной валидации данных;
- нет антиспама/rate-limit/captcha;
- нет единой модели заявки для будущей CRM/бота.

### CustdevQuiz

Сценарий:

- пользователь подписывается на `@garipovdanis`;
- переходит в существующего бота `@finance_razbor_bot`;
- вводит код в интерфейсе сайта;
- проходит 7 вопросов;
- оставляет имя, телефон, Telegram;
- ответы отправляются в `/api/lead`.

Текущая проверка доступа:

- код проверяется на клиенте строкой `ФИНРАЗБОР`;
- реальная проверка подписки выполняется существующим внешним ботом, сайт ее не валидирует.

Риски:

- код доступа легко увидеть в frontend-коде;
- при недоступности `/api/lead` пользователь не получит доставку заявки;
- нет сохранения незавершенной анкеты;
- нет связи заявки с будущей CRM-сущностью.

## 8. API и backend

`server/lead-api.mjs`:

- `GET /health` -> `{ ok: true }`;
- `POST /api/lead` принимает JSON `{ text: string }`;
- отправляет сообщение в Telegram через `https://api.telegram.org/bot<TOKEN>/sendMessage`;
- использует переменные окружения `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`;
- ограничивает body до 32 KB;
- слушает `127.0.0.1:${PORT || 3100}`.

Ограничения:

- нет CORS-настроек;
- нет авторизации/подписи запросов;
- нет rate limiting;
- нет хранения заявок;
- нет поддержки файлов;
- нет webhooks от платежной системы;
- нет обработки статусов;
- нет retry/очереди на случай недоступности Telegram.

Для будущего нового Telegram-бота этот файл можно использовать только как отправную точку, но не как полноценную архитектуру.

## 10. Готовность к Telegram Bot API

Готово:

- есть минимальный серверный endpoint `/api/lead`;
- секреты вынесены в env;
- frontend уже умеет отправлять часть заявок на backend;
- текущий существующий бот отделен от сайта ссылками и не изменяется.

Не готово:

- нет отдельного проекта нового бота;
- нет webhook/polling-архитектуры бота;
- нет модели заявки, статуса, клиента, услуги, тарифа;
- нет загрузки файлов и привязки файлов к заявке;
- нет админ-команд для группы;
- нет маппинга "услуга/тариф -> сценарий";
- нет логирования и хранения истории переписки.

Рекомендация: новый бот делать отдельным backend-проектом или отдельным сервисом внутри репозитория только после согласования. Для текущего сайта сначала подготовить единый API-контракт заявок, чтобы сайт не зависел от внутренних деталей бота.

## 11. Готовность к платежам

Готово:

- сайт может разместить прямые внешние ссылки на Robokassa/СБП без архитектурных изменений.

Не готово:

- нет обработки success/fail callbacks;
- нет проверки факта оплаты на стороне сервера;
- нет связи платежа с заявкой;
- нет защищенной post-payment формы;
- нет idempotency и учета повторных callback'ов;
- нет юридических/SEO страниц под оплату, если они потребуются платежным провайдером.

Без backend-проверки платежей безопаснее на ближайших этапах использовать прямые ссылки и явно маркировать сценарий после оплаты, но полноценная автоматизация потребует серверного слоя.

## 12. Готовность к CRM и админ-панели

Готово:

- заявки уже имеют базовые поля контакта и услуги.

Не готово:

- нет базы данных;
- нет админ-панели;
- нет ролей/доступов;
- нет статусов заявок;
- нет истории действий;
- нет экспорта/интеграции с CRM API;
- нет централизованного backend API для всех форм.

Рекомендация: не начинать с полноценной админ-панели, пока ТЗ Этапа 6 задает администрирование через Telegram-группу. Сначала ввести единую модель заявки и Telegram workflow, затем при необходимости подключать CRM.

## 15. Потенциальные риски

1. Большой компонент `Index.tsx` содержит почти весь лендинг. Любая визуальная правка может случайно задеть соседние секции.
2. Данные услуг частично централизованы в `services.ts`, но важные блоки лендинга и контактов захардкожены в JSX.
3. Текущий `LeadForm` не подтверждает успех Google Sheets webhook из-за `no-cors`.
4. `/api/lead` принимает произвольный текст и не защищен от спама.
5. Проверка кода мини-разбора находится на клиенте.
6. Нет полноценного backend для платежей, документов, CRM и статусов.
7. В проекте смешаны lock-файлы `package-lock.json`, `bun.lock`, `bun.lockb`; это может приводить к несовместимым установкам.
8. SEO-метаданные шаблонные и могут ухудшать поисковое представление сайта.
9. Часть цветов вне утвержденной палитры конфликтует с будущим требованием "не использовать новые цвета".
10. Линтер сейчас не проходит.
11. Нет регрессионных UI-тестов для форм, роутинга и пользовательских сценариев.
12. Существующая сборка содержит крупное hero PNG около 1 MB; при визуальном редизайне важно не ухудшить производительность.

## 16. Безопасная стратегия следующих этапов

Общие правила:

- перед каждым этапом создавать отдельную ветку;
- после каждого этапа делать отдельный commit;
- не переходить к следующему этапу без подтверждения;
- сначала читать `PROJECT_ANALYSIS.md`;
- не менять архитектуру без необходимости;
- не менять фирменный стиль и не вводить новые цвета;
- проверять `vite build`, `vitest run`, целевой lint и визуальную адаптивность.

Рекомендованная последовательность:

1. Визуальные правки выполнять в `Index.tsx`, `ServicePage.tsx`, `index.css` и существующих UI-компонентах минимальными изменениями.
2. Контент услуг менять преимущественно в `src/data/services.ts`; тексты главной страницы менять точечно в `Index.tsx`.
3. Перед платежными сценариями определить единый тип заявки: услуга, тариф, источник, контакт, комментарий, quiz answers, payment status.
4. Для прямых ссылок Robokassa/СБП сначала использовать обычные `<a>`/Button, не имитируя проверку оплаты.
5. Для настоящей проверки оплаты добавить backend callback endpoints и хранение состояния.
6. Новый Telegram-бот разрабатывать отдельно от существующего `@finance_razbor_bot`.
7. Интеграцию сайта с новым ботом делать через единый endpoint заявок, а не через прямую Telegram-логику в компонентах.
8. Если нужна CRM, подключать ее через backend adapter после стабилизации модели заявки.
9. Админ-панель не внедрять в frontend сайта без отдельного ТЗ; для Этапа 6 предпочтительнее Telegram-группа как админ-интерфейс.
